# System Admin — Merchant Management

Open **System Admin → Merchant Management**, `/admin/merchants`.
The shared Admin shell and `manage_users` permission are reused; an explicit System Admin role check also protects the page and all merchant-management APIs. This module does not expose ledger rows or grant financial access.

## Directory and editing

Search merchant name/ID, filter Active/Inactive, and choose 10/25/50 records per page. Filters apply to the full directory. Add Merchant or Edit opens the shared-style two-column dialog; Save requires administrator password reauthentication. Merchant ID is generated by the server and cannot be edited.

Fields: merchant name, existing supported business category, supported country, enabled import base currency, IANA timezone, existing date-display format, and Active/Inactive status. Country and base currency are locked once financial data, balances, simulator activity, imports or applications exist. No historical currency migration or implicit FX conversion is provided. CNY supports transaction imports; it does not introduce simulator tax assumptions.

New merchants contain no accounts, memberships, ledger records or balances. Other business-model inputs start with neutral POC defaults; this editor is not a complete business-assessment questionnaire and zero/default inputs must not be treated as independently verified business facts.

## Assignments and lifecycle

Use existing **User Management → Create/Edit Account → Merchant memberships** to assign an Owner, Staff or Bank. Staff still need explicit delegated grants. Bank membership alone never grants financial-data access: existing Owner authorization, categories, expiry and backend checks still apply. Assignment editing is deliberately not duplicated in this modal.

Inactive merchants retain their records and memberships. Live merchant-scoped authorization denies operations, and business selectors omit them after refresh. Existing conversations/screens may show previously retrieved information until refresh; status changes do not erase historical data already delivered to an authorized user.

## Persistence and APIs

Additive migration `009_merchant_profiles.sql` introduces profile/status/version metadata in the existing identity SQLite database. Existing configured merchants are inserted only if absent; existing profile rows and financial fixtures are not overwritten. Financial settings remain in `merchant_transaction_settings`. Startup restores profiles before currency configuration and ledger projection, including the MCP stdio startup path.

- `GET /api/admin/merchants`: metadata directory and supported editor options.
- `POST /api/admin/merchants`: create profile/configuration only.
- `PATCH /api/admin/merchants/{merchant_id}`: edit; requires the current `expected_version`. The UI also supplies `expected_settings_version` to detect concurrent Owner settings changes.

All writes use the existing journal writer lock, SQLite transaction, live authorization, reauthentication and audit chain. Audit events cover creation, profile/status changes and successful or rejected currency-change attempts. Cookie requests retain existing CSRF and origin checks. No new AI tools are introduced.

## Validation performed

Isolated HTTP/service fixtures: 18 checks passed covering Admin route/shared shell, six preserved configured merchants, Owner/Staff/Bank page and API denial, empty CNY creation, no automatic memberships, edit/stale-version checks, existing-record currency protection, unchanged financial results after rejection, deactivation, selector filtering, restart restoration, audit events and Admin financial-API denial.

Focused Edge browser smoke: 8 checks passed covering sidebar selection, create/search, edit prepopulation/save, locked-currency explanation, mobile dialog width, Escape and no JavaScript errors. Python compilation and JavaScript syntax checks passed.

Full regression, cross-browser verification, extensive responsive testing and load testing: **not run — deferred for the focused POC**.

## Operational limits

Restart the development server to load the new code; its existing startup migration mechanism applies the additive table. No persistent demo database was modified during verification. Back up shared data before normal deployment.

This POC uses one application process with in-memory financial projections. Database changes persist and are restored on restart; multiple simultaneous server processes are not synchronized and are not supported for live profile/currency editing. There is no delete/merge workflow, bulk merchant provisioning, currency migration, custom category editor or full business-input questionnaire. Existing financial formulas, transaction semantics and Bank consent rules are unchanged.
